# Design: Adversary Concurrency Correctness Checklist

## Context

Issue #469 requested a Concurrency Correctness review section
for The Adversary. A 5-agent Divisor triage panel returned
VALID (4/5), unanimous `enhancement`, objective. Two design
questions surfaced during triage and were resolved by the
maintainer:

1. **Domain placement** — production concurrency correctness
   sits at the seam between The Adversary (DoS/resilience) and
   The SRE (efficiency/performance). Resolved: correctness is
   an availability/resilience concern → The Adversary.
2. **Reciprocal SRE edit** — resolved as **Option A**: edit
   only `divisor-adversary.md` in this change; defer the
   reciprocal `divisor-sre.md` Out of Scope row to a follow-up
   issue.

## Goals

- Close the unowned production-concurrency static-review gap.
- Prevent Adversary/SRE finding fragmentation via an explicit
  boundary note.
- Keep the embedded scaffold mirror byte-identical so drift
  tests stay green.

## Non-Goals

- Reciprocal `divisor-sre.md` edit (deferred; tracked as a
  follow-up issue).
- Test-code concurrency review (owned by The Tester).
- Concurrency efficiency/throughput tuning (owned by The SRE).

## Decisions

### D1: Place within Security & Resilience, not a new domain

The Adversary's declared domain is "Security & Resilience" and
already contains "Error Handling and Resilience." Goroutine
leaks (resource exhaustion → DoS) and deadlocks (service
unavailability) are resilience failure modes. The new section
is inserted immediately after "Error Handling and Resilience"
as a numbered subsection, and subsequent sections renumbered.

**Alternative rejected**: a standalone concurrency persona —
disproportionate for a five-item checklist and would fragment
an existing coherent domain.

### D2: Five auditable interrogative items

Items follow the existing checklist's interrogative style
(Are/Is/Could) so each is an auditable review question:

1. Goroutine leaks — spawned without a cancellation/join path?
2. Deadlock — inconsistent lock ordering or unbuffered-channel
   blocking?
3. Unsafe concurrent access — shared map/slice/field without
   synchronization?
4. Missing `context.Context` propagation for cancellation?
5. `sync.WaitGroup` misuse (Add after Wait, missing Done)?

### D3: Scope to production code

An explicit scoping note states the section covers production
code; test-code concurrency remains owned by The Tester
(`divisor-testing.md`), preventing overlap.

### D4: One-directional boundary note (this change)

Add one Out of Scope row on the Adversary side. The reciprocal
SRE-side row is deferred (Option A). Risk: until the follow-up
lands, the boundary is documented on only one side and the SRE
persona may still surface concurrency-correctness findings.
Accepted as a known, tracked gap.

### D5: Dual-copy sync via drift remediation

The canonical source is the repo-root `.opencode/agents/`
copy; the embedded mirror is
`internal/scaffold/assets/opencode/agents/`. The mirror is
regenerated by copying the canonical file
(`cp .opencode/agents/divisor-adversary.md
internal/scaffold/assets/opencode/agents/divisor-adversary.md`).
`TestEmbeddedAssets_MatchSource` enforces byte-identical parity.

## Risks / Trade-offs

- **One-sided boundary (D4)**: mitigated by the tracked
  follow-up issue.
- **Section renumbering churn**: mechanical; no semantic change
  to existing items.

## Verification

Deterministic and offline: `go test -race -count=1
./internal/scaffold/` exercises the drift gate. Item count and
production scoping are verifiable by static inspection of the
single canonical file.
